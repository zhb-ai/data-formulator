# DF 0.7 统一身份与第三方认证接入设计

## 1. 背景

当前 Data Formulator `0.7` 的后端已经从 `0.6` 时代以 `Flask session_id` 为核心的隔离方式，演进为以“身份可信度 + 身份命名空间 + 工作区隔离”为核心的模型。

这意味着后续要接入：

- `Superset` 登录
- `AWS` 账号体系
- `Azure EasyAuth`
- 未来更多第三方认证系统

不应再继续为每个系统单独写一套“登录后塞 session_id”的逻辑，而应基于 `0.7` 已有的身份模型，建立一个统一、可扩展的认证接入层。

本文目标是给出一套适合提交给 DF 作者、也适合后续扩展的统一方案。

---

## 2. 先解释清楚：0.7 升级了什么

### 2.1 `0.6` 的核心模式

`0.6` 的主要边界是：

- 通过 `Flask session` 维护 `session_id`
- 后端以 `session_id` 作为本地数据、DuckDB 文件和接口访问的主要隔离键
- 当接入 `Superset` 登录时，登录成功后继续把 `Superset user` 映射成一个特殊的 `session_id`

这个方案可用，但有两个问题：

1. “用户是谁” 与 “会话是什么” 混在一起
2. 对接多个第三方登录时，容易在各个业务路由中扩散逻辑

### 2.2 `0.7` 的核心升级

`0.7` 做的不是“角色系统升级”，而是：

1. 升级了身份来源的可信度判断
2. 升级了数据隔离的主键模型

具体表现为：

- 可信来源身份会被识别为 `user:<id>`
- 客户端自己上传的标识，只会被识别为 `browser:<id>`
- 工作区、会话保存、Agent 上下文、表数据操作，逐步统一以 `identity_id` 为隔离依据

也就是说，`0.7` 关心的是：

- 这个身份是否可信
- 这个身份是否稳定
- 这个身份是否足够作为数据隔离主键

而不是简单地“当前有没有登录 cookie”。

### 2.3 “身份可信度和数据隔离模型升级”具体指什么

它可以拆成两句话理解：

1. 先判断“你是谁”是否由可信来源证明
2. 再用这个身份去隔离你的工作区、会话、数据和 Agent 执行上下文

例如：

- `Azure` 注入头可以得到 `user:...`
- 将来经过后端校验的 JWT 也可以得到 `user:...`
- 浏览器本地 UUID 只能得到 `browser:...`

因此，`0.7` 已经具备作为统一认证底座的基础。

---

## 3. 这和 Superset 集成的共同点与不同点

## 3.1 共同点

`Superset` 集成与 `0.7` 身份模型有三个明显共同点：

### 共同点 1：都在回答“当前用户是谁”

无论是 DF 自己的身份模型，还是 `Superset` 登录流程，本质上都在解决：

- 当前请求属于哪个用户
- 后续请求如何延续这个用户身份

### 共同点 2：都需要做到用户数据隔离

无论是 `Superset user_42` 还是 `browser:uuid_xxx`，都希望最终形成稳定的用户边界，使不同用户的数据互不干扰。

### 共同点 3：都依赖外部认证结果

`Superset` 认证结果来自 Superset API/JWT。  
`0.7` 当前可信身份也来自外部可验证来源，例如 `Azure EasyAuth` 头或未来可验证 JWT。

本质上，两者都在做同一件事：

**把外部认证系统的结果，映射为 DF 内部可使用的用户身份。**

## 3.2 不同点

### 不同点 1：关注重点不同

`0.7` 更关注：

- 身份来源是否可信
- 身份是否适合作为统一隔离键

而 `Superset` 集成更关注：

- 登录流程是否打通
- 登录后如何保存 token
- 如何用该 token 访问 Superset 数据

### 不同点 2：职责边界不同

`0.7` 的身份模型解决的是：

- DF 内部的工作区隔离
- 会话隔离
- 表和 Agent 上下文隔离

而 `Superset` 自身的 `RBAC/RLS` 解决的是：

- 在 Superset 中这个用户能看什么数据
- 这个用户是否有权限访问特定 dashboard / dataset

因此两者不是替代关系，而是上下层关系：

- `DF identity` 负责“你在 DF 里是谁”
- `Superset permission` 负责“你在 Superset 里能看什么”

### 不同点 3：`0.7` 更适合做统一底座

`Superset` 集成本身是面向单一系统的。  
`0.7` 的 identity 模型则天然更适合扩展为：

- `Superset`
- `AWS Cognito`
- `Azure`
- `OIDC`
- `SAML`
- 其他企业内部认证系统

---

## 4. 设计目标

本方案的目标不是只把 `Superset` 接进去，而是建立一个后续可扩展的统一认证接入层。

设计目标如下：

1. **统一身份主键**
   所有认证用户最终都映射成 DF 内部统一身份键。
2. **业务路由不感知第三方差异**
   `tables_routes`、`session_routes`、`agent_routes` 不应该知道用户来自 `Superset` 还是 `AWS`。
3. **第三方权限继续由第三方负责**
   例如 `Superset` 的 `RBAC/RLS` 应继续由 `Superset` 控制。
4. **支持多 Provider 扩展**
   后续新增 Provider 时，尽量不修改现有业务代码。
5. **兼容匿名模式**
   未登录用户仍可使用 `browser:<uuid>` 作为匿名身份。
6. **后端掌握最终身份判定权**
   前端不能自行决定自己是 `user:*`。

---

## 5. 推荐方案：统一身份层 + Provider 插件化

推荐采用：

**统一身份层（Identity Layer） + Provider 插件化（Auth Provider）**

### 5.1 总体结构

```text
Browser / Frontend
    |
    |  发起登录 / 携带匿名 browser identity
    v
DF Auth Entry
    |
    |-- AzureProvider
    |-- SupersetProvider
    |-- CognitoProvider
    |-- OIDCProvider
    |
    v
Principal / IdentityResolver
    |
    v
identity_key = user:<provider>:<subject>
    |
    +--> Workspace isolation
    +--> Session save/load
    +--> Tables
    +--> Agents
```

### 5.2 统一身份对象

建议在 DF 内部引入统一的 `Principal` 概念：

```ts
type Principal = {
  provider: string;
  subject: string;
  username?: string;
  email?: string;
  display_name?: string;
  groups?: string[];
  roles?: string[];
  raw_claims?: Record<string, unknown>;
}
```

后端统一生成：

```text
identity_key = user:<provider>:<subject>
```

示例：

- `user:superset:42`
- `user:cognito:8f3c...`
- `user:azure:7b91...`
- 匿名用户仍为 `browser:<uuid>`

这样设计有三个好处：

1. 避免不同 Provider 的用户 ID 冲突
2. 业务层只认 `identity_key`
3. 后续新加 Provider 不需要重做数据隔离模型

## 6. 推荐的模块划分

建议新增一个统一认证目录，例如：

```text
py-src/data_formulator/authn/
    __init__.py
    models.py                # Principal / AuthResult
    resolver.py              # get_identity_id / resolve_principal
    session_store.py         # provider session state read/write
    providers/
        __init__.py
        base.py              # AuthProvider 抽象
        azure.py             # Azure EasyAuth
        superset.py          # Superset login / token refresh / me
        cognito.py           # AWS Cognito / OIDC
```

### 6.1 `AuthProvider` 建议抽象

```python
class AuthProvider:
    name: str

    def authenticate(self, request) -> AuthResult | None:
        ...

    def refresh(self, session_state: dict) -> AuthResult | None:
        ...

    def get_principal(self, session_state: dict) -> Principal | None:
        ...

    def logout(self, session_state: dict) -> None:
        ...
```

### 6.2 `AuthResult` 建议结构

```python
@dataclass
class AuthResult:
    principal: Principal
    session_state: dict
    access_token: str | None = None
    refresh_token: str | None = None
```

### 6.3 `IdentityResolver` 职责

统一负责以下逻辑：

1. 先看后端 session 中是否已有已验证 `Principal`
2. 再尝试可信头或可验证 JWT
3. 再尝试 Provider 自动恢复
4. 最后才退回 `browser:<uuid>`

注意：

- 前端发送的 `X-Identity-Id` 只能作为匿名 fallback
- 它不能直接决定用户是否为 `user:*`

## 7. Superset 应如何接入

`Superset` 在本方案中，应被视为一个 **认证 Provider + 外部权限系统**。

### 7.1 Superset Provider 职责

`SupersetProvider` 负责：

1. 转发用户名密码登录，或接收 SSO bridge 回来的 token
2. 调用 `/api/v1/me/` 获取已验证用户信息
3. 构造 `Principal(provider="superset", subject="<user_id>")`
4. 将 token 和必要的 provider session state 保存到后端 session
5. 提供自动 refresh 能力

### 7.2 Superset 在 DF 内部的身份映射

Superset 用户成功登录后，应映射为：

```text
user:superset:<superset_user_id>
```

而不再继续把它仅仅处理成一个自定义 `session_id`。

### 7.3 Superset 与 DF 的职责边界

#### DF 负责

- 识别该用户在 DF 中的身份
- 为该用户分配工作区和会话隔离空间
- 让 DF 内部接口统一用 `identity_key`

#### Superset 负责

- 验证该用户是否登录
- 决定该用户可访问哪些 dataset / dashboard
- 执行 `RBAC` 和 `RLS`

这能最大程度减少 DF 内部重复实现权限系统的复杂度。

## 8. AWS 账号接入应如何设计

这里要明确区分两种场景。

### 8.1 场景 A：用户用 AWS 账号登录 DF

这种情况下，建议优先考虑：

- `AWS Cognito`
- 或 `AWS Identity Center` 背后的 `OIDC/SAML`

统一接入方式：

- Provider 完成认证
- DF 得到稳定 `subject`
- 映射为 `user:cognito:<sub>` 或 `user:aws-sso:<subject>`

### 8.2 场景 B：DF 访问 AWS 资源

例如：

- `S3`
- `Athena`
- `Redshift`

这个不应直接等同于“用户登录身份”。  
建议拆成另一层：`CredentialBinding` 或数据源连接配置。

也就是说：

- “谁登录 DF” 是身份问题
- “DF 用什么权限访问 AWS 资源” 是数据源授权问题

两者可以有关联，但不应该混为一个模型。

### 8.3 为什么要分开

否则会出现以下问题：

- 用户用 `Superset` 登录 DF，却不能访问 S3，因为他不是 AWS 登录用户
- 或用户是 AWS 登录用户，但其实只想访问 Superset，而不需要 AWS 数据权限

统一身份层的意义是：

**先确定“用户是谁”，再单独决定“用户可以绑定哪些外部资源能力”。**

## 9. 推荐的数据模型与会话策略

### 9.1 DF 内部统一身份键

统一使用：

```text
browser:<uuid>
user:<provider>:<subject>
```

### 9.2 后端 session 中建议保存的信息

建议后端 session 只保存：

- `principal`
- `provider_name`
- `provider_session_state`

而不是把各种业务路由直接耦合到：

- `session["superset_token"]`
- `session["superset_user"]`
- `session["session_id"]`

推荐统一成：

```python
session["auth"] = {
    "provider": "superset",
    "principal": {
        "provider": "superset",
        "subject": "42",
        "username": "alice",
        "email": "alice@example.com",
        "display_name": "Alice",
        "roles": [],
        "groups": [],
    },
    "provider_state": {
        "access_token": "...",
        "refresh_token": "...",
        "expires_at": 1712345678,
    }
}
```

### 9.3 业务代码只读统一身份

业务代码不直接解析 provider token，而是统一调用：

- `get_current_principal()`
- `get_identity_id()`

这样可以避免第三方接入细节扩散到业务层。

## 10. 推荐的请求处理顺序

### 10.1 匿名用户

1. 前端生成浏览器 UUID
2. 请求中携带 `X-Identity-Id`
3. 后端解析为 `browser:<uuid>`
4. 工作区按该 identity 隔离

### 10.2 已登录 Superset 用户

1. 用户完成 `Superset` 登录或 SSO
2. 后端拿到 Superset token 并获取 `/me`
3. 后端构造 `Principal(provider="superset", subject="<id>")`
4. 后端 session 中保存统一 `auth` 对象
5. `get_identity_id()` 返回 `user:superset:<id>`
6. 所有业务路由按这个 identity 隔离
7. 访问 Superset 数据时继续使用 `Superset token`

### 10.3 已登录 AWS Cognito 用户

1. 用户完成 Cognito 登录
2. 后端校验 token 或完成 OIDC 回调
3. 构造 `Principal(provider="cognito", subject="<sub>")`
4. `get_identity_id()` 返回 `user:cognito:<sub>`
5. DF 内部工作区和会话统一隔离

---

## 11. 与当前 `0.7` 的结合方式

建议不要在 `tables_routes.py`、`session_routes.py`、`agent_routes.py` 中增加任何面向 `Superset` 或 `AWS` 的专有判断。

正确接入点应该是：

### 11.1 统一认证入口

改造 `auth.py` 或将其重构为 `authn/resolver.py`，使其支持：

- 已验证 `Principal`
- 可信 header
- 已验证 JWT
- 匿名 browser identity

### 11.2 登录/登出/回调端点

由 Provider 单独提供：

- `/api/auth/login`
- `/api/auth/logout`
- `/api/auth/me`
- `/api/auth/providers/<provider>/callback`

### 11.3 前端状态

前端只需要感知：

- 当前是否已登录
- 当前 `principal`
- 当前 `identity_key`
- 启用了哪些 Provider

而不是直接耦合到某个系统专有字段。

## 12. 为什么这是最适合提交给 DF 作者的方案

这个方案相对容易被上游接受，原因如下：

1. **符合 `0.7` 已有方向**
   `0.7` 已经引入了 identity 模型，这个方案是在其基础上抽象化，而不是推翻重做。
2. **不会把 Superset 特性硬编码进核心业务路由**
   这比“为了 Superset 改一堆路由”更容易被接受。
3. **对未来更多第三方系统有扩展价值**
   作者更容易接受一个通用能力，而不是单一系统特化。
4. **保持匿名模式兼容**
   不会破坏 DF 当前无登录即可使用的体验。
5. **职责边界清晰**
   DF 管身份和隔离，第三方系统管它自己的认证与权限。

---

## 13. 不推荐的方案

### 不推荐 1：继续以 `session_id` 为中心扩展

问题：

- 与 `0.7` 现有 identity 模型方向不一致
- 第三方接入越多，越难维护

### 不推荐 2：每增加一个 Provider 就修改多个业务路由

问题：

- 路由层污染严重
- 测试复杂度快速上升
- 很难被上游接受

### 不推荐 3：前端自行决定自己是 `user:*`

问题：

- 容易造成身份伪造
- 破坏 `0.7` 已建立的可信身份边界

---

## 14. 推荐的实施顺序

建议按以下顺序推进。

### Phase A：统一抽象

1. 引入 `Principal`
2. 引入 `AuthProvider`
3. 将 `get_identity_id()` 改为统一 resolver

### Phase B：兼容现有 `0.7`

1. 保留 `browser:<uuid>` 匿名模式
2. 保留 Azure EasyAuth 入口
3. 业务路由改为只依赖统一 identity

### Phase C：接入 Superset

1. 实现 `SupersetProvider`
2. 支持 login / me / refresh / logout
3. 将 Superset 用户映射为 `user:superset:<id>`
4. 将 Superset 数据访问继续建立在其 token 与 `RBAC/RLS` 上

### Phase D：接入 AWS

1. 实现 `CognitoProvider` 或通用 `OIDCProvider`
2. 将 AWS 用户映射为 `user:cognito:<sub>` 或 `user:aws-sso:<subject>`
3. 后续再根据需要拆分资源授权能力

---

## 15. 结论

结论如下：

1. `0.7` 的升级重点不是“多了角色系统”，而是“身份可信度 + 身份命名空间 + 数据隔离主键”的升级。
2. 你的 `Superset` 集成与 `0.7` 的共同点在于都在解决“用户是谁”和“如何按用户隔离数据”。
3. 两者的不同点在于：
   - `0.7` 解决 DF 内部统一身份与隔离
   - `Superset` 解决外部认证与外部数据权限
4. 最合适的落地方案是：
   **统一身份层 + Provider 插件化**
5. 该方案既能支持 `Superset`，也能支持 `AWS`，并为未来接入其他第三方系统预留标准扩展点。

---

## 16. 建议的后续代码改造方向

建议后续代码层面聚焦以下改造点：

- 新增统一认证目录 `py-src/data_formulator/authn/`
- 重构 `auth.py` 为统一 `IdentityResolver`
- 将 `Superset` 认证改造成 `SupersetProvider`
- 前端新增统一 `auth state`，不要直接耦合 `Superset` 字段
- `workspace/session/agent/tables` 统一只依赖 `identity_key`
